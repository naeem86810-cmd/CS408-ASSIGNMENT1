## 1. Introduction

A small JavaScript web application is being built by a student team where every member uses a different computer. The team has faced three recurring problems: inconsistent code formatting, missing packages on some machines, and difficulty finding browser errors. Question 1 designs and justifies a shared development environment that removes these problems. Question 2 shows a safe Git and GitHub workflow for publishing and collaborating on a Node.js project, including how to react when a push is rejected.

The overall idea is that the environment should be reproducible (anyone can set it up the same way), consistent (everyone formats code the same way), and observable (errors can be located quickly).

## 2. Question 1: Design, Set Up, and Justify a Development Environment

### 2.1 Part (a): Essential tools and why they are selected

Each tool solves a different problem, so the team needs all of them rather than a single replacement.

| Tool | Category | Main purpose | Problem it solves for the team |
|---|---|---|---|
| VS Code | Code editor | Writing, navigating, and debugging code with a built-in terminal and Git support | Gives everyone one common workspace |
| ESLint | VS Code extension | Analyses code and reports likely bugs and rule violations while typing | Catches errors such as unused variables before running the code |
| Prettier | VS Code extension | Automatically formats code (indentation, quotes, semicolons) | Removes formatting inconsistency between members |
| EditorConfig | VS Code extension | Applies shared basic settings (indent size, line endings) across editors | Avoids Windows/Mac/Linux line-ending and tab differences |
| Node.js | Runtime | Runs JavaScript outside the browser (scripts, servers, build tools) | Provides the engine for npm, dev servers, and the backend |
| npm | Package manager | Downloads, installs, and updates libraries and records them in package.json | Fixes the missing-packages problem |
| Browser Developer Tools | Browser debugging tool | Inspects HTML/CSS, JavaScript errors, network requests, and stored data | Makes browser errors visible and traceable |
| React DevTools | Browser extension | Shows the React component tree with props, state, and hooks | Debugs React-specific issues that normal DevTools cannot show clearly |

**Reasoning behind the choices.**

- **VS Code** is free, works on all operating systems, and has a large extension ecosystem. The `.vscode/settings.json` and `.vscode/extensions.json` files in this repository make "format on save" and the recommended extensions identical for everyone.
- **ESLint and Prettier** have different jobs. ESLint checks code *quality* (possible bugs); Prettier handles code *style* (how it looks). Using both, with configuration files stored in the repository, means style arguments never reach code review.
- **Node.js** is needed because modern JavaScript tooling runs on it. The team should agree on one LTS version, written in the `engines` field of package.json, to avoid "works on my machine" problems.
- **npm** is installed together with Node.js, so no extra setup is needed. Yarn or pnpm are valid alternatives, but the team must choose only one so that two different lockfiles do not appear.
- **Browser Developer Tools** are built into Chrome, Edge, and Firefox and are the first place to look when a page misbehaves.
- **React DevTools** is essential only if the app uses React. It adds to, and does not replace, the normal Developer Tools, because it understands components, props, and state.

### 2.2 Part (b): package.json, dependencies, development dependencies, and the lockfile

**package.json** is the project's description file. It stores the name, version, scripts (for example `npm start`), and the packages the project needs. Because it is committed, a new team member does not need to be told which packages to install; one command is enough.

**Dependencies** are needed while the application is *running* in production. For example, `express` is required by a server every time it starts. They are installed with `npm install express` and appear under `"dependencies"`.

**Development dependencies** are needed only while *writing, testing, or building* the code. They are installed with `npm install --save-dev eslint` and appear under `"devDependencies"`. Separating them keeps the production install smaller (`npm install --omit=dev`).

*Example:* **ESLint** (or Prettier, Jest, nodemon) is a development dependency, because the deployed application never needs it to run; it is only used by developers to check code. In contrast, **express** or **react** must exist at runtime, so they are normal dependencies.

**Lockfile (package-lock.json).** Version ranges in package.json (for example `^4.18.0`) allow npm to pick any compatible newer version. Without a lockfile, two members installing on different days could receive different versions, causing bugs that appear on only one computer. The lockfile records the *exact* version of every package, including nested sub-dependencies. When it is committed, `npm ci` installs the same tree on every machine.

The `package.json` of this project:

```json
{
  "name": "cs408-assignment1",
  "version": "1.0.0",
  "scripts": {
    "start": "node app.js",
    "lint": "eslint .",
    "format": "prettier --write ."
  },
  "engines": { "node": ">=18" },
  "devDependencies": {
    "eslint": "^9.0.0",
    "prettier": "^3.2.0"
  }
}
```

**How this helps the team:** package.json answers "what does the project need?", the lockfile answers "which exact versions?", and together they make `npm install` or `npm ci` enough to rebuild the same environment on any computer. This directly solves the missing-package issue.

### 2.4 Part (d): Debugging a wrong output and a failed image request

The page `public/index.html` in this repository reproduces both faults: the total is shown as `105` instead of `15`, and `images/logo.png` does not exist.

| Panel | What I would check | Evidence it can provide |
|---|---|---|
| **Console** | Red error messages and `console.log` output | JavaScript errors with file name and line number; messages such as `Failed to load resource: 404` for the image; the logged values `price`, `tax`, `total` |
| **Sources** | Set breakpoints and step through the code | The real value and type of variables at each step, so the exact line where the calculation goes wrong can be found |
| **Elements** | The live DOM and the applied CSS | Whether the wrong text is a data problem or only a display problem (hidden by CSS, wrong element updated, wrong `src` on the `<img>` tag) |
| **Network** | Every request made by the page (filter by *Img* and *Fetch/XHR*) | For the image: request URL, status code (404, 403, blocked), and headers. For wrong output: the API response body, to see whether the server sent wrong data or the front end processed it wrongly |

**Reasoning for the wrong output.** First open **Console**, because an error usually points directly to the cause. If there is no error, use **Network** to check whether the data received from the server is correct. If the data is correct, the problem is in my code, so I place a breakpoint in **Sources** and watch the variables. In this demo the variables are strings (`'10'` and `'5'`), so `+` joins them as `'105'`. The fix is to convert them with `Number()`. **Elements** finally confirms what the browser rendered.

**Reasoning for the failed image.** In **Network**, a red entry with status 404 means the path is wrong. Typical causes are a mistyped filename, different upper/lower case (Linux servers are case sensitive, Windows is not), a path relative to the wrong folder, or the file not committed to Git. I compare the request URL with the real file location and check the `src` attribute in **Elements**. If the status is 200 but nothing is shown, the file may be corrupted or have a wrong content type, which the response headers reveal.

**React DevTools** supports this in a React app: the *Components* tab shows props and state of each component, which helps decide whether wrong output comes from wrong state or from wrong props passed by a parent.

## 3. Question 2: Git/GitHub Workflow and Troubleshooting Scenario

### 3.1 Part (a): Core commands to publish the project

The scenario starts with a local folder that already contains `app.js` and `package.json` and has one initial commit.

**1. Check the repository state**

```bash
git status
```

Shows which files are modified, staged, or untracked, and the active branch. Run it before and after every other step to avoid committing unwanted files (for example the large `node_modules` folder).

**2. Stage and commit changes** (after `.gitignore` is created, see part b)

```bash
git add .gitignore app.js package.json package-lock.json
git commit -m "Add .gitignore and project files"
```

`git add` moves chosen changes to the staging area, so I decide exactly what goes into the next snapshot. `git commit` saves the staged snapshot to local history with a message that explains the change. Naming files explicitly avoids staging accidental files.

**3. Make sure the branch is called main**

```bash
git branch -M main
```

Renames the current branch to `main`, the standard default on GitHub.

**4. Connect the local repository to GitHub**

First create an empty repository on GitHub (without README, so there is no unrelated history), then:

```bash
git remote add origin <REPOSITORY_URL>
git remote -v
```

`git remote add origin` stores the GitHub address under the short name `origin`. `git remote -v` shows the stored addresses so I can confirm the URL. `<REPOSITORY_URL>` is a placeholder such as `https://github.com/username/project.git`.

**5. Push the main branch**

```bash
git push -u origin main
```

Uploads local commits of `main` to the remote. `-u` sets `origin/main` as upstream, so later `git push` and `git pull` work without extra arguments.

**Authentication note:** a personal access token or SSH key is used for login. These secrets must never be written in the repository, README, or screenshots.

### 3.2 Part (b): Why node_modules is ignored

`node_modules` contains every installed package and all sub-dependencies. It is excluded from Git because:

- **Size:** it can hold thousands of files and hundreds of megabytes, which makes cloning and pushing slow and may exceed GitHub file-size limits.
- **It can be regenerated:** its content is fully described by package.json and the lockfile, so storing it adds no information.
- **Platform differences:** some packages contain binaries compiled for a specific operating system or Node version, which can break installation on a teammate's computer.
- **Noisy history:** installing or updating a package changes many files and hides the real changes during review.

The relevant `.gitignore` entries:

```gitignore
# Dependencies
node_modules/

# Environment variables and secrets
.env

# Logs and system files
npm-debug.log*
.DS_Store
```

If `node_modules` was already committed by mistake, adding it to `.gitignore` is not enough because Git keeps tracking existing files. It must be removed from tracking (not from disk):

```bash
git rm -r --cached node_modules
git commit -m "Stop tracking node_modules"
```

**Role of package.json and the lockfile for another developer.** A teammate who clones the repository receives only source code, package.json, and package-lock.json. package.json says which packages are required and the lockfile says which exact versions. Then:

```bash
git clone <REPOSITORY_URL>
cd cs408-assignment1
npm install     # or npm ci for an exact, clean install
```

npm creates a local `node_modules` with the same versions as everyone else. `npm ci` is especially suitable for teamwork and automated builds because it follows the lockfile strictly and fails if the lockfile and package.json disagree.

### 3.3 Part (c): Commit, branch, push, pull, and clone

| Term | Meaning | Example |
|---|---|---|
| **Commit** | A saved snapshot of the staged changes in local history, with author, time, and message | `git commit -m "Add login route"` |
| **Branch** | A separate line of development that lets work continue without changing the main line | `git switch -c feature/login` |
| **Push** | Sends local commits to a remote repository such as GitHub | `git push origin feature/login` |
| **Pull** | Gets new commits from the remote and integrates them into the current branch (a fetch followed by merge or rebase) | `git pull origin main` |
| **Clone** | Makes a full local copy of a remote repository with its history and sets up `origin` automatically | `git clone <REPOSITORY_URL>` |

**How branches and commits reduce the risk of overwriting work in this scenario.** The teammate has already made changes on a separate branch. This is a safe arrangement, because their work is isolated from `main` and from my branch, so neither of us can accidentally break the other's code. Collaboration works as follows:

1. Each person develops a feature on its own branch (for example `feature/login` and `feature/navbar`), and `main` is kept in a working state.
2. Small commits with clear messages produce a history that can be reviewed, compared, and reverted individually if one change causes a problem.
3. Every commit has a unique identifier, so Git knows which changes are new on which side. When branches are merged, Git combines changes automatically if they touch different places, and stops with a conflict (instead of silently overwriting) if both changed the same lines.
4. Changes reach `main` through a pull request, where the teammate can review them and tests can run before the merge.
5. Before starting new work I run `git fetch` or `git pull`, and I can inspect the teammate's branch with `git branch -a` and `git log origin/their-branch` without modifying my own files.

In short, branches provide isolation, commits provide traceable history, and merge conflicts act as a safety alarm, so no one's work is lost without notice.

### 3.4 Part (d): Safe troubleshooting of a rejected push

A typical error message:

```text
! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/username/project.git'
hint: Updates were rejected because the remote contains work that you do not have locally.
```

This means the remote `main` has commits that my local `main` does not have (for example the teammate pushed, or the GitHub repository was created with a README). Git refuses the push because accepting it would erase those remote commits. The error is a protection, not a failure of the setup.

**Safe approach, step by step:**

1. **Read the message and check local state.** Run `git status` to make sure the working directory is clean; commit or stash unfinished work.
2. **Fetch without changing my files.**
   ```bash
   git fetch origin
   ```
3. **Inspect the difference** between local and remote:
   ```bash
   git log --oneline --graph --all
   git log main..origin/main --oneline
   git diff main origin/main
   ```
4. **Integrate the remote commits.** Either normal method is acceptable:
   ```bash
   git pull --rebase origin main    # replays my commits on top of the remote ones (linear history)
   # or
   git pull origin main             # creates a merge commit
   ```
   If Git reports "refusing to merge unrelated histories", I check why the histories differ before using `--allow-unrelated-histories`.
5. **Resolve conflicts if any.** Open files marked with `<<<<<<<`, `=======`, `>>>>>>>`, keep the correct combination of both versions (discussing with the teammate if needed), then run `git add <file>` and `git rebase --continue` (or `git commit` for a merge).
6. **Test the project.** Run `npm install` and `npm start` (and tests if available), because a merge can be textually clean but still break the application.
7. **Push again.**
   ```bash
   git push origin main
   ```

**Why blindly overwriting remote history is risky.** `git push --force` makes the remote branch equal to my local branch, which permanently deletes any remote commits I do not have. This can destroy the teammate's work, break everyone else's local copies (their history no longer matches the remote), make it hard to see who changed what, and hide mistakes. Recovery through reflog is sometimes possible but difficult and not guaranteed. If a force push is truly necessary (for example after removing an accidentally committed secret), it should be done only after telling the team, preferably on a personal branch, and with `git push --force-with-lease`, which refuses to overwrite if the remote changed unexpectedly.

## 5. Conclusion

A reliable team environment depends on standardisation. VS Code with ESLint, Prettier, and EditorConfig keeps formatting uniform. Node.js with npm, controlled by package.json and a committed lockfile, ensures every computer installs the same packages. Browser Developer Tools and React DevTools shorten the time needed to locate faults. In the Git workflow, a `.gitignore` that excludes node_modules keeps the repository small and clean, feature branches and pull requests separate the work of different members, and a careful fetch, inspect, integrate, test, push routine solves rejected pushes without risking a teammate's commits.
